# Institution workspace and school community

Added **20 October 2026**. Requires backend migrations 024–028 and coordinated frontend/backend deployment. Migration 025 adds school replies; 026 adds administrator comments/replies; 027 adds persistent community notifications; 028 adds private moderation reasons and suspension-email delivery tracking. Local implementation does not mean it is live. No live school is claimed/activated just by installing this code.

## School representative

1. Choose **Sign in**, then the **Institution** account tab (or the institution link in the footer). Use `/institution/register` for a new contact account; `/institution/login` for an existing one. The header shows one sign-in and one create-account action; on institution pages they keep institution context. Both account types use the shared student-style auth layout and a segmented account switch.
2. Select one existing school using search. If missing, choose **My school is not in the directory** and fill the official name/type/address/city/coordinates/website/description form.
3. Provide your designation, contact telephone, official public verification link, and how admin can independently verify your authority. Do not submit IDs, passwords, or private student records.
4. Accept the current agreement, submit, and verify the emailed code. Email ownership is not school authority.
5. Sign in to `/institution` to track review. Pending/rejected/suspended accounts cannot edit or publish. New schools are not public until approved. Only an approved account reserves a school: suspension makes it selectable for a new institution registration, which still requires email verification and admin approval. There is one approved owner at a time; no staff-team or rejected-application resubmission workflow is provided yet. This requires backend migration 032 and the matching API; no frontend deployment alone changes reservations.
6. Once approved/active, `/institution` opens your school page directly. Use **Edit profile** in the profile header, the camera on the logo, **Edit school photos** on the cover, **Add program** beside Programs offered, and **Create post** in the header or School posts composer. Existing offerings/posts have their own edit/remove controls. Editors open in dialogs on the page; cancel/escape/navigation protects unsaved changes. Save after uploading images; an upload alone is not attachment. Use permitted PNG/JPEG/WebP images up to 4 MB.
7. Link existing catalog programs and edit only your own offering/fee/source/description/requirements/careers. New school-owned titles can be edited while unshared; shared catalog metadata remains protected. Removing an offering does not delete another school's program.
8. Write text announcements/events/admissions updates with an optional HTTPS link and up to six photos. New posts default to **Publish now** and go live immediately when saved; there is no separate per-post admin approval. Choose **Draft — not public** when needed. Institution ownership approval still applies. The School posts tab has a private **Drafts & moderated posts** management list for the owner, plus the public feed. Publishing does not override admin moderation. **View as visitor** hides owner tools and private drafts; it does not change permissions. There are no direct messages.

Owner tools require the signed-in, verified institution's own approved/active school. Another school's page, students, and public visitors receive no editor controls. The API still authorizes every mutation independently; hiding buttons is not the security boundary. Pending/rejected/suspended/inactive institutions stay on the application-status screen.

Institution accounts cannot use student assessment/saved/comparison/dashboard workflows. Password recovery reuses existing email recovery. Institution Google sign-in is not included; use the separate password login.

### Institution account settings

Open **Account settings** in the main navigation, own-school management bar, or application-status page (`/institution/settings`). The two-card design matches student Profile settings. **Institution information** edits the public name of the school already linked to the account (1–190 characters), not the registered representative's personal name. Contact email and representative name stay read-only; no ownership-switch or home-location controls are shown. Only approved owners of active schools can rename. Name changes update the existing school record, preserve its ID/programs/posts/claim, and are audited; original application evidence is not rewritten. Conflicting or stale name changes are rejected; use **Reload account details** to refresh. Save the name before submitting a password change.

**Change password** is available to verified institution accounts even while pending/suspended. Enter the current password and a different matching new password, 8–72 characters and at most 72 UTF-8 bytes. Each password is masked with its own show/hide control. Successful changes clear reset codes, revoke the institution account's refresh sessions, clear credentials in this browser and return to institution sign-in. Existing access JWTs elsewhere can remain valid until their configured expiry; this is not instant global sign-out. No real account credentials are changed by local fixture/browser tests. The two forms save independently and protect unsaved edits. This update requires matching backend/frontend code but no extra migration beyond the institution/community schema already listed above.

Registration is grouped into representative details, account details, one-school selection/request, and authority verification. Visible counters/native maxlength controls match server-side registration limits: each name 20; contact email 190; position 100; telephone 30; verification instructions 1000; school name 190; city 100; campus address 255; HTTPS links 2000; new-school description 2000. Passwords require 8–72 characters and no more than 72 UTF-8 bytes, with matching confirmation; verification codes are six digits. Numeric latitude/longitude use geographic bounds rather than character limits. Existing saved applications/profiles are not truncated or rewritten. Registration remains unsaved-change protected and requires the policy checkbox; limits do not bypass email or authority approval.

Student sign-up uses the matching top-aligned registration layout, personal/account sections and shared `AccountField` controls. It retains its own existing limits (names 20, home address 50, email 40), Google sign-up, policy agreement and email-verification flow. Sharing a visual design does not give students institution permissions or change either registration API.

### Name and telephone validation

Student registration/profile and institution representative names allow Unicode letters, accents and ordinary spaces only. Digits, punctuation (including apostrophes/hyphens), emoji, hidden characters and control characters are rejected, not silently stripped. Optional middle names can remain empty. New-school requests and institution renames allow letters, accents, digits and spaces, but no special characters. Existing catalog choices are selected by ID; their stored names are not rewritten. Program titles, addresses, passwords, links and free-text descriptions do not inherit personal-name restrictions.

School contact telephone must be a string of ASCII digits (`0`–`9`), up to the existing 30-character limit. Enter `0281234567` or `63281234567`, not a formatted `+63 ...` number. Leading zeros remain intact. Shared native form patterns, visible instructions and JavaScript submit validation are backed by server checks before saving or sending registration email. Google-imported identity names and existing saved records are not bulk-changed by this form-validation update. No migration is required.

## Student school page

**Programs offered** remains the default. **School posts** appears beside it only when the API confirms an approved institution owner with verified/active contact and an active school. Unregistered/pending/rejected/suspended/inactive schools have no public post tab.

Visible posts/comments can be read without signing in. Verified student accounts can like/unlike, comment, and delete their own comments. Comments display the student's first name, not an email. Like counts are public; liker lists are not. Do not publish contact details or private records. Filters/pagination and moderation can remove a post from view; hidden/draft posts cannot receive new interactions.

Approved institutions can use **Reply as school** below a student's comment on their own published posts. Replies show the school name and **School reply** label, not the representative's personal name/email. Institutions cannot like, start student comments, or reply on another school's posts. Students cannot impersonate school replies. Each author may delete their own comment/reply. Hiding or removing a student comment also hides its reply thread from the public feed/counts. Replies cannot be nested further; students can start a new comment to continue a conversation.

Verified administrators can start a comment or use **Reply as administrator** beneath a root comment on any visible school post. Public comments show **Administrator**, never the sign-in email or personal name. Schools may also reply beneath administrator root comments on their own posts. Replies stay one level deep; admins cannot publish onto draft/hidden/inactive-school posts. Likes remain student-only. Own deletion and existing hide/restore moderation still apply; hiding/removing any parent hides its replies. From admin institution moderation, use **Open school page → School posts** to participate in the public discussion.

## Application search

The admin **School applications** tab includes a status-scoped search by existing/requested school name, representative full name, or contact email. Search runs on the server before the 200-result limit, case-insensitively with literal wildcard characters; it is bounded to 100 characters. The UI debounces requests, ignores stale responses, and provides loading, retry, empty and clear-search states. The API remains verified-admin-only and no-store. No migration is needed for application search.

## Notifications

Verified students and institutions have a header bell. Institutions receive new likes, comments and administrator replies on their own active school's posts; students receive school/administrator replies to their own root comments. The admin **Activity center** receives only replies in root comment threads that administrator has participated in, not unrelated likes/comments or other threads on the same post. Its scraping activity and system-log links remain unchanged. Self-interactions do not notify the actor. No follow-school subscriptions, new-post broadcasts or browser push notifications are implemented.

The badge shows unread visible activity. Open an item to mark it read and open that exact school post with comments expanded, even when it is older than the first feed page. **View all school posts** returns to the full feed. **Mark all read** applies through the current snapshot; later arrivals remain unread. Read status is server-stored per account. The inbox has 20-item pages with **Older notifications**, loading/error/retry/empty states, outside-click/Escape dismissal and a mobile layout. It refreshes on opening and every 60 seconds while visible and closed; it is not real-time push. Account changes reset all inbox state.

Only new interactions after migration/deployment generate notifications; historic likes/comments are not backfilled. Duplicate/repeated likes generate at most one notification per liker/post/recipient, including unlike/re-like. Removed likes and hidden/deleted posts/comment threads are omitted from ordinary activity. Suspending/deactivating school ownership removes ordinary community notices from visible inboxes. Previews show public first names, school names or generic Administrator attribution, not sign-in emails or copied comment text. There is still no public liker list. Public feed permissions remain authoritative when opening ordinary activity.

Hide/restore decisions notify the actual post/comment author with the administrator's required reason. A private notice dialog shows the reason and saved school/post title without navigating to hidden content or discarding unsaved forms. These decision notices remain readable only by the affected account even after hiding/deletion or school suspension. They are not public announcements or retroactive notices.

Institution suspension also creates a private reason notice and emails that reason to the registered institution account after the suspension commits. The admin application queue shows SMTP delivery state and **Retry suspension email** for pending/failed/interrupted attempts. A `sent` state means accepted by SMTP, not guaranteed inbox delivery; errors do not reverse suspension. Attempts use a two-minute lease; superseded/restored suspension notices are cancelled before sending. No automatic worker is installed, so unresolved attempts require admin retry. A lost database acknowledgement after SMTP acceptance can cause duplicate mail on retry. Ordinary activity and hide/restore notices are in-app only. This feature does not add student account suspension controls.

## Administrator

Every application status includes a labeled **Representative details** section: full/first/middle/last name, position/designation, institution contact email, school telephone, email-verification status, submission date, official authorization URL and verification instructions. Optional or older missing fields show **Not provided**, not guessed values. Evidence links open separately and must use HTTPS. These saved registration/account details are read-only and admin-only; passwords, hashes and security codes are never included. This is not a new historical snapshot or an ownership-verification shortcut. Existing approval, suspension and decision-reason controls remain below the details.

Use **Admin → Institution accounts** (`/admin/institutions`). Review pending requests, contact a trusted school channel independently, and enter a decision reason. Approval requires verified contact email plus an explicit authority-verification confirmation. New-school details can be corrected before approval. Approved/suspended views allow suspension/restoration with a reason. Suspension releases the school's registration reservation and disables that account's school access. A suspended account can be restored only if another account has not already been approved for the school; the API explains conflicts. Accounts, application history and existing school content are preserved.

The **Posts & comment moderation** view starts with **Select a school**, a university-management-style table with school logos, type/city, activation, post counts, name/city search, and six-school pages. Activated registered institutions are shown by default; use **All registered schools** or **Inactive / suspended schools** to review content after suspension. Schools without an approved/suspended institution identity are not included in this selector. Click a school name or **View posts** to open only that school's posts; **Change school** returns to selection.

The selected school's complete nondeleted post history is available in 20-post pages, including drafts, published posts, hidden posts, full text, images/captions and links. **Search this school's posts** searches titles/content across all pages (up to 100 characters), resets to page one on query changes, and stays scoped to the selected school. **Clear search** restores the list. **Review comments** opens the existing bounded comment review. The panel can hide/restore posts and comments with an audit reason. Editing a post as the institution cannot unhide it. Approval/restoration pauses the school's scraping sources so unattended collection cannot overwrite its work; re-enable only after a deliberate conflict review.

Verified administrators see **Delete school post** only in the admin moderation list, not in the public school feed. Their public commenting/reply controls remain available. Confirmation is required for post deletion. This marks the post deleted and removes it from the feed and school editor; schools cannot republish the deleted record. Related comments/likes and the moderation audit remain stored (not a physical purge). Use Hide/Restore for reversible visibility moderation. Student/institution roles cannot call the admin delete endpoint; approved institutions retain their separate own-post management controls.

## Privacy and implementation limits

Terms/Privacy version `2026-10-20-v2` adds representative evidence, public posts/comments/likes, and moderation/image-retention notices. Existing acceptance timestamps are not fabricated. Policies still require project-owner review and a real public contact/retention/minor-user process.

Uploaded images are public/cached assets; hiding a post does not revoke copied image links. Post deletion/comment removal is visibility removal, not a promise that audit records/backups disappear. Posts are plain text, not executable HTML. Browser/API controls are not a complete moderation or anti-abuse operation.

The owner sees the latest 100 posts; admin queue up to 200 applications per status; public feed pages 10 posts and comments/replies each page 20, newest first. Admin post counts include nondeleted hidden comments/replies for moderation; public counts include only visible threads. No private messaging, multiple representatives per school, or self-service rejected-application resubmission is implemented. Do not describe these as completed features.
